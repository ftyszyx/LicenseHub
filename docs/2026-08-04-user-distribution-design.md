# 用户分销功能设计方案

## 1. 背景与目标

LicenseHub 已具备商品套餐、支付订单、支付通知、注册码发放和后台用户管理能力。分销功能需要建立在现有订单支付链路上，使用户能够分享推广链接，并在推广订单支付成功后获得佣金。

本方案遵循以下已确认原则：

- 整个分销功能由管理员“系统设置”中的总开关控制，默认关闭；关闭时不向用户开放功能。
- 所有用户默认拥有推广能力，不设置“分销员”角色。
- 不新增独立的分销员资料表，推广配置统一归入 `users`。
- 用户登录现有后台后，可以查看自己的推广数据和佣金记录。
- 管理员继续通过现有 RBAC 权限管理全站佣金业务。
- 注册码生成、绑定和验证逻辑不因分销功能发生变化。
- 佣金以独立流水记录，不直接在用户表中维护一个可变余额。
- 项目已经上线，所有表结构变更必须通过 migration 添加对应 SQL，并提供 up/down migration。

## 2. 当前实现范围

当前实现一级分销：一个订单最多归因给一个推广用户，只产生一笔推广佣金。

包含：

- 为所有用户生成唯一推广码。
- 用户查看并分享推广链接。
- 购买页识别推广码并在下单时提交。
- 后端在创建订单时完成推广归因并固化佣金快照。
- 支付成功、发放注册码时生成待确认佣金。
- 佣金经过观察期后转为可结算。
- 退款或订单撤销时取消、冻结或冲正佣金。
- 用户和管理员分别查看权限范围内的数据。
- 用户提交全部或部分可用佣金的提现申请，默认一次申请全部可用佣金。
- 提现申请仅支持支付宝账户，管理员线下转账后登记打款流水并上传凭证。
- 提现中的 `locked` 佣金在退款时自动驳回申请并取消对应佣金。
- 已打款的 `settled` 佣金退款后生成负向调整，后续佣金优先抵扣欠款。

当前不包含：

- 多级分销、团队奖或区域代理。
- 分销资格申请与审核。
- 自动向微信、支付宝或银行卡打款。
- 支付宝开放平台自动转账。
- 多触点营销归因。
- 访问量、独立访客等复杂推广统计。

## 3. 核心业务流程

```text
用户获取推广链接
    ↓
访客通过推广链接进入购买页
    ↓
前端保存并在下单时提交 referral_code
    ↓
后端验证推广码并将归因、比例、佣金金额写入订单
    ↓
支付渠道通知支付成功
    ↓
同一事务内发放注册码、更新订单、创建佣金流水和订单事件
    ↓
观察期结束后佣金变为可结算
    ↓
用户查看可提现佣金并提交提现申请
    ↓
系统按佣金产生顺序锁定申请金额
    ↓
管理员线下转账，登记打款流水并上传凭证
    ↓
结算单完成，锁定金额转为已结算
```

分销逻辑只附着于订单链路，不进入注册码验证链路。无推广码、推广码无效或推广用户不符合归因规则时，订单仍可正常创建和支付，只是不产生佣金。

## 4. 数据模型

以下字段均已通过 migration 实现。

### 4.1 用户表 `users`

已增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `referral_code` | `VARCHAR(32)` | 唯一推广码，由系统生成，不直接暴露用户 ID |
| `commission_rate_bps` | `INTEGER NULL` | 用户个人佣金比例，单位为万分比；为空时使用系统默认值 |
| `settlement_account` | `JSONB NULL` | 支付宝收款账户信息 |

约束建议：

- `referral_code` 建立唯一索引。
- `commission_rate_bps` 为空或处于 `0..10000`。
- 普通用户不能自行修改推广码和个人佣金比例。
- 收款账户的敏感字段不能出现在普通日志中。

当前收款方式仅支持支付宝。`settlement_account` 保存支付宝账号和收款人姓名，例如：

```json
{
  "account": "user@example.com",
  "real_name": "张三"
}
```

后端只开放支付宝提现接口，并校验支付宝账号和收款人姓名不能为空。后续增加其他收款方式时，可以在 JSON 中增加账户类型字段，同时继续保留结算单中的历史账户快照。

### 4.2 订单表 `orders`

已增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `referrer_user_id` | `INTEGER NULL` | 推广用户，外键指向 `users.id` |
| `referral_code` | `VARCHAR(32) NULL` | 下单时使用的推广码快照 |
| `commission_rate_bps` | `INTEGER NULL` | 下单时的佣金比例快照 |
| `commission_amount_cents` | `INTEGER NULL` | 下单时计算的佣金金额快照，单位为分 |

这些字段在创建订单时写入，支付通知阶段不得根据用户当前配置重新计算。即使管理员之后修改比例或重置推广码，历史订单也保持不变。

### 4.3 佣金流水表 `distribution_commissions`

已实现字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `order_id` | `INTEGER` | 来源订单 |
| `user_id` | `INTEGER` | 获得佣金的推广用户 |
| `order_amount_cents` | `INTEGER` | 订单实付金额快照 |
| `commission_rate_bps` | `INTEGER` | 佣金比例快照 |
| `commission_amount_cents` | `INTEGER` | 佣金金额 |
| `status` | `SMALLINT` | 佣金状态 |
| `available_at` | `TIMESTAMPTZ NULL` | 可结算时间 |
| `locked_amount_cents` | `INTEGER` | 已被待处理提现申请锁定的金额 |
| `settled_amount_cents` | `INTEGER` | 已完成线下打款的金额 |
| `cancelled_amount_cents` | `INTEGER` | 因退款等原因取消的金额 |
| `adjustment_amount_cents` | `INTEGER` | 用于抵扣历史退款欠款的金额 |
| `cancel_reason` | `TEXT NULL` | 取消、冻结或冲正原因 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 更新时间 |

约束建议：

- 对 `order_id` 建立唯一约束，确保一个订单最多产生一笔佣金。
- 金额均使用整数分，不使用浮点数。
- 佣金金额不得小于零。
- `user_id` 和 `order_id` 均建立索引。
- `status`、`available_at` 建立组合索引，便于佣金解冻任务扫描。
- 四个分配金额均不得小于零，合计不得超过原佣金金额。
- 结算单与佣金通过 `distribution_settlement_items` 关联，同一笔佣金允许按金额部分锁定和部分结算。

### 4.4 订单退款记录表 `order_refunds`

当前使用人工退款确认模式：管理员先在微信、支付宝等支付渠道完成全额退款，再在订单管理中填写退款凭证和原因。系统在同一事务内写入退款记录、将订单改为已退款、撤销注册码授权、取消或冲正佣金并写入订单事件。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `refund_no` | `VARCHAR(64)` | 系统生成的唯一退款记录号 |
| `order_id` | `INTEGER` | 来源订单，一张订单最多一条成功退款记录 |
| `amount_cents` | `INTEGER` | 全额退款金额快照，单位为分 |
| `provider` | `VARCHAR(32)` | 支付渠道 |
| `provider_trade_no` | `VARCHAR(128) NULL` | 原支付渠道交易号 |
| `refund_reference` | `VARCHAR(255)` | 管理员填写的外部退款凭证 |
| `reason` | `TEXT` | 退款原因 |
| `operator_user_id` | `INTEGER` | 确认退款的管理员 |
| `refunded_at` | `TIMESTAMPTZ` | 退款确认时间 |

该记录表示支付渠道退款已经由管理员确认完成，系统当前不会主动调用微信或支付宝退款接口。

### 4.5 结算单表 `distribution_settlements`

已实现字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `settlement_no` | `VARCHAR(64)` | 唯一结算单号 |
| `user_id` | `INTEGER` | 申请结算的用户 |
| `amount_cents` | `INTEGER` | 结算金额 |
| `status` | `SMALLINT` | 结算状态 |
| `settlement_account` | `JSONB` | 提交申请时的收款账户快照 |
| `payment_reference` | `VARCHAR(255) NULL` | 打款流水号或凭证编号 |
| `payment_proof_file_name` | `VARCHAR(255) NULL` | 打款凭证文件名 |
| `payment_proof_content_type` | `VARCHAR(128) NULL` | 打款凭证类型 |
| `payment_proof_size` | `BIGINT NULL` | 打款凭证大小 |
| `reject_reason` | `TEXT NULL` | 拒绝原因 |
| `requested_at` | `TIMESTAMPTZ` | 申请时间 |
| `reviewed_at` | `TIMESTAMPTZ NULL` | 审核时间 |
| `paid_at` | `TIMESTAMPTZ NULL` | 打款时间 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 更新时间 |

结算单必须保存收款账户快照，避免用户修改账户后影响历史记录。同一用户最多存在一笔待处理提现申请。

`distribution_settlement_items` 记录结算单从每笔佣金中锁定的金额，用于支持部分提现。`distribution_settlement_proofs` 保存受权限保护的打款凭证二进制内容；第一版支持 JPG、PNG、WebP 和 PDF，单个文件最大 `5 MB`。

### 4.6 佣金调整流水表 `distribution_commission_adjustments`

已结算佣金对应的订单发生退款时，不修改原佣金流水和历史结算单，而是新增负向调整流水。已实现字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `user_id` | `INTEGER` | 需要抵扣佣金的用户 |
| `order_id` | `INTEGER` | 发生退款的来源订单 |
| `original_commission_id` | `BIGINT` | 原已结算佣金流水 |
| `amount_cents` | `INTEGER` | 调整金额，退款冲正时为负数 |
| `offset_amount_cents` | `INTEGER` | 已通过后续佣金抵扣的金额，使用正数记录 |
| `reason` | `VARCHAR(64)` | 调整原因，例如 `refund` 或 `manual_adjustment` |
| `status` | `SMALLINT` | 待抵扣、部分抵扣、已抵扣或已取消 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 更新时间 |

约束建议：

- `amount_cents` 必须小于零，欠款绝对值为 `abs(amount_cents)`。
- `offset_amount_cents` 必须大于等于零，且不能超过欠款绝对值。
- 同一退款业务和原佣金只能创建一笔有效调整流水，通过唯一约束保证幂等。
- 原佣金流水及已完成结算单保持不变，调整流水单独参与用户可提现金额计算。
- `distribution_commission_adjustment_offsets` 记录每次由哪笔新佣金抵扣了多少欠款，便于审计。

## 5. 推广码与归因规则

### 5.1 推广码生成

- 新用户注册或管理员创建用户时自动生成推广码。
- migration 需要为现有用户回填唯一推广码。
- 推广码使用随机字符串，例如 `AB12CD34`，不使用连续用户 ID。
- 创建和重置时依赖数据库唯一索引处理碰撞，并在冲突后重试。
- 普通用户只能查看推广码，不能自行修改。
- 管理员重置推广码后，旧推广链接停止用于新订单，历史订单不受影响。

推广链接示例：

```text
/products?ref=AB12CD34
```

### 5.2 前端保存

购买页读取 `ref` 参数后保存在浏览器中，并在创建订单时提交。

“推广归因有效期”是指访客点击某个用户的推广链接后，该推广关系在浏览器中保留的时间。系统默认设置为 `30 天`。例如访客在 8 月 1 日点击推广链接，只要在有效期内完成下单，订单仍归因给该推广用户；超过有效期后下单则不再归因。管理员可以在“系统设置”页面修改该天数，配置仅影响新记录或后续重新写入的推广归因。

推荐采用“最后一次有效推广访问覆盖”规则：

- 新的有效推广码覆盖浏览器中尚未过期的旧推广码。
- 无效推广码不覆盖已有有效归因。
- 到期后前端不再提交推广码。

浏览器保存只用于改善体验，最终有效性必须由后端判断。

### 5.3 后端归因

创建订单请求增加可选字段：

```json
{
  "plan_id": 1,
  "pay_type": "wechat_native",
  "referral_code": "AB12CD34"
}
```

后端处理顺序：

1. 根据推广码查询用户。
2. 推广码不存在时忽略归因，不影响正常下单。
3. 读取用户个人佣金比例；为空时读取系统默认比例。
4. 根据订单金额计算佣金。
5. 将用户、推广码、比例和佣金金额作为快照写入订单。

当前商城购买不要求买家登录，因此第一阶段无法完全识别自购行为。若后续购买流程绑定登录用户，应禁止 `buyer_user_id == referrer_user_id` 的订单产生佣金。

## 6. 佣金规则

### 6.1 计算方式

比例使用万分比，金额使用整数分：

```text
commission_amount_cents = floor(amount_cents × commission_rate_bps / 10000)
```

例如订单金额为 `9900` 分、比例为 `1500`：

```text
floor(9900 × 1500 / 10000) = 1485 分
```

计算时需要使用足够宽的整数类型作为中间值，避免两个 32 位整数相乘溢出。

### 6.2 比例优先级

当前采用：

```text
用户个人比例 > 系统默认比例
```

系统设置已增加：

- `distribution_enabled`：分销总开关，初始值为 `false`，由管理员在“系统设置”页面开启。
- `distribution_default_rate_bps`：默认佣金比例，初始值为 `2000`，即 `20%`。
- `distribution_attribution_days`：推广归因有效期，初始值为 `30`，即访客点击推广链接后 `30 天`内完成下单仍归因给该推广用户。
- `distribution_holding_days`：佣金观察期，初始值为 `7`，即订单支付成功产生佣金后需要等待 `7 天`才能成为可结算佣金。
- `distribution_min_withdraw_cents`：最低提现金额，初始值为 `5000`，即 `50 元`。

总开关关闭时：

- 用户后台隐藏推广中心入口，用户不能访问推广数据和佣金页面。
- 用户分销接口返回明确的“分销功能未开启”业务错误，不能只依赖前端隐藏入口。
- 购买页不保存或提交推广码。
- 创建订单时忽略推广码，不建立新的推广归因和佣金快照。
- 支付成功时不为关闭期间创建的订单生成佣金。
- 已存在的历史推广订单和佣金数据不会删除或重新计算。
- 管理员仍可查看历史推广订单和佣金数据。

总开关重新开启后，只对重新开启之后创建的新订单生效。关闭期间创建的订单即使在重新开启后才支付，也不应补记佣金，应以订单创建时是否成功建立推广归因为准。

管理员可以在现有“系统设置”页面维护默认佣金比例、推广归因有效期、佣金观察期和最低提现金额：

- 默认佣金比例使用百分比展示和输入，后端及数据库统一转换为万分比保存。例如管理员输入 `20%`，实际保存值为 `2000`。允许的输入范围为 `0%..100%`，修改后只影响新创建的订单，不重新计算历史订单和佣金流水。
- 推广归因有效期使用天数展示和保存，默认 `30 天`。它控制访客点击推广链接后，多久内创建的订单仍算作该用户的推广订单。
- 佣金观察期使用天数展示和保存，默认 `7 天`。它控制订单支付成功后，佣金需要等待多久才能从 `pending` 转为 `available`；观察期内发生退款时可以直接取消佣金。
- 最低提现金额使用元展示和输入，后端及数据库统一转换为分保存。例如管理员输入 `50 元`，实际保存值为 `5000`，用户提交提现申请时后端强制校验。

### 6.3 佣金状态

当前定义：

| 状态 | 含义 |
| --- | --- |
| `pending` | 支付成功，处于退款观察期 |
| `available` | 观察期结束，已成为可提现佣金 |
| `locked` | 已被结算申请锁定 |
| `settled` | 已完成打款 |
| `cancelled` | 订单退款、作废或其他原因取消 |
| `offset` | 已用于抵扣历史退款产生的佣金欠款 |

状态流转：

```text
pending → available → locked → settled
    └──────────────→ cancelled
```

提现申请被拒绝时，关联佣金从 `locked` 恢复为 `available`。

## 7. 支付成功与幂等处理

佣金应在现有支付成功事务中创建，顺序建议为：

```text
锁定订单
→ 校验支付渠道与金额
→ 生成注册码
→ 更新订单为已交付
→ 创建 pending 佣金流水
→ 创建订单事件
→ 提交事务
```

支付通知可能重复发送，必须同时依赖：

- 已交付订单的现有幂等判断。
- 佣金表 `order_id` 唯一约束。
- 同一数据库事务。

不能在支付事务提交后再异步创建佣金，否则可能出现订单已经发码但佣金缺失的情况。

## 8. 退款与佣金冲正

当前注册码撤销表示软件权益被收回，不等同于支付渠道已经退款。退款处理需要区分：

- 注册码权益撤销。
- 支付渠道退款申请。
- 支付渠道退款成功。
- 订单退款状态。
- 佣金取消或冲正。

当前已实现规则：

- `pending` 或 `available` 佣金：退款成功后将未结算金额改为 `cancelled`。
- `locked` 佣金：自动驳回包含该佣金的待处理提现申请，释放其余锁定金额，再取消退款订单对应佣金。
- `settled` 佣金：保留历史结算单和打款记录，创建等额负向调整，后续新佣金优先抵扣。
- 已用于抵扣旧欠款的佣金发生退款时，为已抵扣部分重新创建负向调整，恢复相应欠款。
- 管理员不能通过注册码页面撤销已完成付费订单的授权，必须使用订单退款确认入口。
- 订单退款确认使用事务和订单行锁；重复确认直接返回已有退款结果，不会重复撤销授权或佣金。
- 已退款订单收到重复支付成功通知时保持已退款状态，不重新发码或创建佣金。

当前退款操作为人工确认流程：管理员必须先在支付渠道完成全额退款，再在订单管理中填写外部退款凭证和原因。系统不会自动调用微信或支付宝退款接口，也不支持部分退款。

已结算佣金退款后的抵扣规则确定如下：

1. 原佣金继续保持 `settled`，原结算单继续保持已完成，不修改历史打款记录。
2. 退款成功后，按原已结算佣金金额创建一笔负向调整流水。
3. 用户后续产生的新佣金完成观察期后，优先按时间顺序抵扣尚未结清的负向调整，再计算可提现金额。
4. 抵扣不足时保留剩余欠款，用户推广中心显示待抵扣金额。
5. 用户存在未结清负向调整时不能申请提现，后端必须先完成抵扣核算。
6. 欠款全部抵扣后，调整流水标记为已抵扣，剩余佣金才进入正常可提现范围。
7. 不自动从用户支付宝账户追回已经打款的佣金；长期无法通过新佣金抵扣时，由管理员根据调整流水进行线下处理。

示例：订单产生并已结算 `20 元`佣金，之后订单退款。系统保留原 `20 元`已结算记录，并创建 `-20 元`调整流水。用户后来新增 `12 元`佣金时先抵扣欠款，仍欠 `8 元`；再新增 `15 元`佣金时抵扣剩余 `8 元`，最终只有 `7 元`可以进入可提现金额。

管理员执行支付渠道退款后，必须通过统一的订单退款确认操作触发订单、注册码、佣金、退款审计记录和订单事件的联动，不能仅修改注册码状态。

## 9. 提现与结算

用户可以选择部分提现，也可以一次结算全部可用佣金。提现页面默认选择当前全部 `available` 佣金并填入全额，用户可主动调整为不低于最低提现金额的部分金额。

用户申请提现时：

1. 校验达到最低提现金额。
2. 开启数据库事务。
3. 按确定的顺序选择并锁定足以覆盖申请金额的 `available` 佣金，默认锁定全部可用佣金。
4. 计算金额并创建结算单。
5. 将佣金改为 `locked` 并关联结算单。
6. 提交事务。

最后一笔佣金大于剩余申请金额时，通过 `distribution_settlement_items.amount_cents` 和佣金分配金额字段只锁定所需部分，不拆分原始佣金流水。

管理员处理：

- 审核拒绝后将佣金恢复为 `available`。
- 管理员在线下完成支付宝转账后，填写打款流水号并上传凭证，将结算单改为已打款、锁定金额改为已结算。
- 系统不调用支付宝自动转账接口，打款动作由管理员在线下完成。

后端必须校验申请金额、当前可用佣金和最低提现金额，并在事务中按 `available_at`、佣金 ID 顺序锁定金额。用户存在待抵扣欠款或已有待处理提现申请时，不允许再次申请。

## 10. 接口建议

### 10.1 用户接口

```text
GET  /api/me/distribution/summary
GET  /api/me/distribution/commissions
GET  /api/me/distribution/settlements
POST /api/me/distribution/settlements
GET  /api/me/distribution/settlements/{id}/proof
GET  /api/me/distribution/adjustments
```

项目当前实际路由位于 `/api/admin/me/distribution/...`，由登录鉴权中间件获取当前用户。上表省略了现有 `/admin` 路由前缀，用于表达用户本人接口的语义。

用户接口必须从 JWT 获取当前用户 ID，不接受客户端指定查询目标用户。

### 10.2 管理员接口

```text
GET  /api/admin/distribution/commissions
GET  /api/admin/distribution/settlements
POST /api/admin/distribution/settlements/{id}/reject
POST /api/admin/distribution/settlements/{id}/paid
GET  /api/admin/distribution/settlements/{id}/proof
GET  /api/admin/distribution/adjustments
PUT  /api/admin/users/{id}/commission-rate
POST /api/admin/users/{id}/referral-code/reset
```

管理员接口沿用现有 RBAC：佣金、结算单和调整流水查询使用 `distribution:read`，拒绝提现、确认打款和读取敏感打款凭证使用 `distribution:update`。所有用户默认拥有推广能力，不代表所有用户默认拥有管理员接口权限。

## 12. 安全与审计

- 所有普通用户查询必须强制限定当前 JWT 用户。
- 用户分销接口必须在后端校验 `distribution_enabled`，关闭时拒绝访问。
- 推广码只能用于查找归因用户，不能作为登录或鉴权凭证。
- 支付金额、佣金比例和佣金金额均由后端计算。
- 支付成功、佣金创建、退款、结算审核和打款均保留数据库记录。
- 收款账户和打款凭证按敏感信息处理，日志中需要脱敏。
- 管理员修改佣金比例只影响新订单。
- 退款和结算状态变更使用事务和行锁，数据库唯一索引限制同一用户只能存在一笔待处理提现，防止重复提现和重复冲正。

## 14. 实施顺序

建议按以下顺序开发：

1. migration、SeaORM Entity 和系统设置。
2. 用户推广码生成与历史数据回填。
3. 创建订单归因和佣金快照。
4. 支付成功事务内创建佣金。
5. 用户推广数据查询接口与推广中心。
6. 佣金观察期转换机制。
7. 订单退款、注册码撤销和未结算佣金取消联动。
8. 提现申请、结算单、支付宝账户和管理员线下打款记录。
9. `locked` 退款撤销与 `settled` 退款负向调整。
10. 全链路测试与后台数据统计。

上述一级分销、人工退款确认、提现申请、线下打款登记、打款凭证、`locked` 撤销和 `settled` 负向调整均已实现。数据库结构通过 `202608041000_distribution`、`202608051000_order_refunds` 和 `202608051100_distribution_settlements` migration 逐步增加。
